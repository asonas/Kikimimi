# Phase 1 設計の経緯

Phase 1 の設計は `design.md` とスケッチ（`sketch/`）がすべてである。この文書は、それがどう組み立てられたかの記録で、実装の根拠にはしない。

## 比べたもの

2 つのモデルに同じ前提資料（DESIGN.md、Phase 0 で確かめた事実、ユーザーの他の macOS アプリの project.yml）を渡し、互いに見せずに設計させた。候補 A（Opus）と候補 B（Sonnet）である。arena の手順では別系統のモデルによる判定（cross-judge）を挟むが、今回の候補は Claude 系だけで別系統のモデルがなかったので、判定は省き、リードが両案を読んで決めた。

両案は次の点で独立に同じ結論に達したので、強い合意とみなした。XcodeGen のアプリターゲットとローカル SwiftPM パッケージに分けること。全構成で同じ Bundle ID を使うこと。収録中は CAF（16bit LPCM mono）に追記し、停止時に AAC へ変換すること（両案とも SIGKILL を実際に起こして確かめた）。停止と復元で同じ finalize を使うこと。収録中かどうかをロックファイルの `flock` で決めること。セッションの状態を保存せず、ファイルから導出すること。欠落を無音で埋めること。segments.json をフィルタ前のまま持つこと。WhisperKit を 1 インスタンスで順に動かし、書き起こし中は通信しないこと。マイクをデバイス UID とチャンネルで選び、既定の入力に切り替えないこと。画面収録の許可後は利用者の操作で再起動すること。

## B を土台にした理由

- B のスケッチは純粋ロジック（状態遷移、時計の方針、ロック、meta の往復）を実装済みで、9 テストが通っていた。A は型だけだった。
- 時刻のずれについて、B は 0.1 秒を超える欠落を埋め、逆戻りのジャンプだけを削る。2 時間のずれを正負両方向でシミュレーションしてテストしていた。A は 0.5 秒を超える欠落だけを埋める。
- B は録音の状態機械と書き起こしのキューを分けていて、復元や再書き起こしの置き場所が自然だった。
- B は WhisperKit をパッケージ内の専用ターゲットに置き、アダプタをコンパイル検査とテストの対象にしていた。
- B のコミット計画は各コミットに検証方法が付き、最初のハードウェア関連のコミットで TCC 許可の引き継ぎを確かめる。

## A から取り込んだ点

1. finalize は 48kHz を超える CAF を 48kHz に変換してから AAC に書く。AAC エンコーダが 96kHz と 192kHz で失敗することを A が確かめた（`evidence-a/aac-sample-rates.swift`）。
2. 自分トラックのサンプルが 3 秒以上すべて 0.0 なら即座に警告する。判定は TrackClock が欠落を埋める前のソースのバッファに対して行う。
3. DEBUG ビルドのヘッドレス実行（`--headless record`、`--headless transcribe`）。UI と同じ controller のメソッドを呼び、起動は必ず `open -n` で LaunchServices を通す。
4. Transcriber のポートをセッション単位にした。モデルのロード、処理順、アンロードはアダプタに閉じ込め、`EngineOutput.normalize` は Core に残した。
5. 音声の読み込みに `AudioInputOptions(audioLoadingMode: .incremental)` を使う。
6. 再起動は `/usr/bin/open -n <bundle>` を実行してから自身を終了する。
7. タスクは `scripts/` ではなく `mise.toml`（`generate`、`test`、`build`、`app`）に置く。

## 取り込まなかった点

- 1 つの Phase で書き起こしまで持つ形。B の分け方でも「次の面接を優先する」は満たせ、復元や再書き起こしも素直に書ける。
- transcript.md の手編集をハッシュで検出して退避する仕組み。Phase 1 では `transcript.prev.md` の 1 世代で足りる。Phase 2 で Obsidian 側を上書きするときに検討する。
- segments.json のフィールド名を `track` にする案。DESIGN.md §6 の `speaker` のままにした。
- パッケージを `Packages/RecorderKit` に置く案。YoruMimizuku に合わせて `core/` にした。
- 書き起こし中もロックを持つ案。ロックが取られたフォルダは「収録中」と判定されるので、書き起こし中のセッションが収録中と表示されてしまう。

## 利用者が決めたこと

1. pause は Phase 1 に入れない。休憩するときは停止して新しいセッションにする。
2. DESIGN.md §5 の 1 本の状態遷移を、録音の状態機械と書き起こしのキューに分ける。
3. 起動時に復元したセッションは自動で書き起こさず、メニューから手動で始める。
4. 既定のモデルは `openai_whisper-large-v3-v20240930_turbo`。圧縮版（約 630MB）との日本語の精度の差は測っていない。
5. 録音中の一時ファイルは 1 時間あたり約 0.7GB（2 トラック分）。空き容量が 5GB 未満なら開始を拒否する。

## 統合のときに決めたこと

取り込みを `design.md` とスケッチに反映する過程で、次の点を決めた。詳細は `design.md` にある。

- モデルはセッションごとにロードしてアンロードする。キューが空になったときにアンロードする B の方式はやめた。
- 進捗はアダプタがトラックごとの割合を返し、Core の `TranscriptionProgress` が長さで重み付けして単調にする。処理順はアダプタが決めるので、Core は順番に依存しない。
- 取り消しが遅い場合の代替策（いまのトラックを終えてから止める）は、トラックの境界を知っているアダプタに置く。
- 再起動とヘッドレス実行はどちらも `open -n` で 2 つ目のインスタンスを起こす。そのため `LSMultipleInstancesProhibited` は設定せず、AppDelegate の「すでに起動していれば終了する」処理は、通常の起動のときだけ行う。
- 自分トラックの健全性は `SilenceMonitor` だけが決め、レベルによる無音とデジタル無音を優先順位付きでまとめる。
- スケッチはコミット 2（`core/`、`mise.toml`）とコミット 4（`App/`、`project.yml`）でリポジトリに移し、同じコミットでこのディレクトリから消す。
